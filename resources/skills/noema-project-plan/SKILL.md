# 规划与审查

结构由 `plan` 校验（整体写入，`--dryRun` 先试；同 id 即修改），机械问题由 `check` 找出。
这里只讲判断。

## 拆分

- 按数据流、契约边界、写入归属或可独立验证的验收来拆，不按惯性分层；测试跟着被验证的事走。
- 一个任务交给一个 Agent 一次做完。说不清验收就还没想清楚。规模相称，三个任务够就别写十个。
- `after` 只写真实阻塞，相关而不阻塞写 `related`。会改同一批文件的并行任务，加 `after` 或用 worktree。
- 高风险、改契约、难回退的加 `review: required`。

## 正文

领取者只一定读正文：一句结果目标、文件引用（不贴长文）、范围、`- [ ]` 可复核的验收。

## 审查

用户要求或计划较大时做，默认只报告。以用户原话和当前代码为准，不以计划自身为准。

先列主要价值流，每条走一遍：输入 → 处理 → 存储 → 消费方 → 输出 → 失败路径 → 验证，
逐格对应任务 id，空格就是缺口。任务再多，端到端断了也不算覆盖。

再看：有生产者无消费者的对象；改契约却没覆盖调用方；并行任务其实不独立；
只有 mock 或无调用方的路径被算作交付。

输出 `PASS`、`NEEDS_REVISION` 或 `BLOCKED`，附证据和修改顺序。
