# Noema 审计报告 (2026-06)

性能 / 可靠性 / 笔记系统三面审计。约束:不改变现有体验,仅安全优化。
本轮已应用的改动见末尾「本轮改动」一节。

## 总体结论:架构健康,有未来

- **md 是唯一真相源**,CM6 `EditorState` 是运行时唯一权威,preview 是对 source 的视图
  (见 `CLAUDE.md` 不变量 1–3)。md frontmatter / `#+begin meta` / Typst metadata
  三格式合并合理,可长期演进。
- **补全走后端实时查询**(version 失效缓存),不是 client 缓存 + 广播。
- 编辑热路径已做过 8 轮性能优化(见 `docs/perf-memory-upgrade.md`):viewport 增量
  token、按字节预算缓存、history 上限、StateField 存在性短路、CJK 行级缓存、
  完整 `destroy()` 清退。
- **Emacs 侧 md-roam 的全缓冲扫描全部按需触发,不在每次按键路径上** —— 编辑发生在
  web app,Emacs 只是 shim,因此不影响打字延迟。

审计只发现少量残留隐患,不是系统性问题。

## 性能:5MB 大文件编辑延迟

CM6 各 StateField 在 `docChanged` 时的重扫策略实测如下:

| 字段 | 普通字符 | 结构字符 (`# > | ` ~`) | 换行 (Enter) |
|---|---|---|---|
| `markdownTablesField` | map | `updateMarkdownTablesNearChanges`(窗口) | 同左,窗口 |
| `tableDecoField` | map | `patchTableDecosNearChanges`(窗口) | 同左,窗口 |
| `htmlBlockDecoField` | map | `patchHtmlBlockDecosNearChanges`(窗口) | 同左,窗口 |
| `lineDecoField` | map | `patchLineDecosNearChanges`(窗口) | **旧:`buildLineDecos` 全文** |

**关键发现(已修):** `lineDecoField` 是唯一例外 —— `canMapLineDecos` 与
`canPatchLineDecosNearChanges` 都对 `\n` 短路,导致**每次按 Enter** 都走
`buildLineDecos(tr.state)` = 对整篇 5MB 文档跑 `syntaxTree.iterate`(强制全量解析)。
这是大文件里仅存的"每键 O(document)"路径。

> 注:计划最初怀疑的 `markdownTablesField` 触 `|` 全扫,实测**已被
> `expandedTableLineWindow` 限定为窗口**,`?? collectMarkdownTables` 那条回退几乎是
> 死路径。真正的残留在 `lineDecoField` 换行分支。

**修复(行为保持、有同文件先例):** 让换行走 `patchLineDecosNearChanges`(近改动窗口),
与 `htmlBlockDecoField` 一致 —— 该字段一直无条件近改动打补丁(含换行)。
`patchLineDecosNearChanges` 的窗口已覆盖连续表格行与代码围栏,换行的结构影响被覆盖;
`@@part`/`@@section` 语义标题仍走全量重建(它们跨窗口重新编号)。修复后换行不再做
whole-doc `buildLineDecos` 的全文 `iterate` + 全文 decoration set 重建,最坏情形降为
O(所在块)而非 O(文档)。

**关于收益的诚实标注:** 本修复**逻辑正确、有同文件先例、在浏览器中有真实收益**
(浏览器 viewport 懒解析下,换行触发的全文 `iterate` 会强制解析未解析区,且每键重建
全文 decoration set 有 GC 压力)。但**当前 happy-dom 测试环境无法量化它**:5MB 语法树
在 `lineDecoField.create` 时已被全量解析,缓存树上的全文 `iterate` 很便宜 —— 实测换行
延迟 fix 前 ~278ms / fix 后 ~276ms,在噪声内。因此守护测试以"不退化到全文 Lezer 解析
那一档(`$$` 的 ~1081ms)"为目标,而非声称测得了延迟下降。

**已知边界(本轮不动,正常笔记不触发):** 单个超大连续块(如一张 >数百行的巨表 /
一段巨型代码块)被编辑时,窗口会沿块边界外扩到整块 = O(块)。研究笔记不会有这种
退化文档,故不加截断上限(加上限会有把巨表 widget 切片的视觉回归风险)。

## 性能:服务端索引吞吐

**发现(本轮仅记录,未改):** `patchResolvedRelationships`(`runtime.mjs:2490`)是写好的
关系增量打补丁函数,且 `buildRelationshipCache` / `notesRelationshipCache` 已接好,
**但从未被调用** —— 增量扫描路径(`runtime.mjs:2604`)仍调用全量
`resolveNoteRelationships(rawNotes)`,对整库重算 refs/backlinks。

- 影响:每次"保存触发的增量扫描"关系解析是 O(全库 notes + refs),不是 O(脏文件)。
  属吞吐问题,**不影响每键编辑延迟**(编辑在浏览器;扫描在 Node)。
- 未做原因:接入需改索引路径行为,且该函数有 null 回退(命中则退回全量)以保正确性,
  需配独立测试。建议作为后续单独改动:把增量分支改为
  `patchResolvedRelationships(notesSnapshot, dirty, dirtyNotes) ?? resolveNoteRelationships(rawNotes)`,
  并加针对"脏文件 ref 变更/未变更"两类的回归用例。

## 可靠性

1. **未捕获错误曾被静默吞掉(已修):** `web-host.mjs` 的 `uncaughtException` /
   `unhandledRejection` 仅写 stderr,既不退出也不通知前端,服务端可能半坏继续运行。
   现在改为额外 broadcast 一个 `command: "server-error"` 的 SSE 诊断(有界、截断 500 字),
   保留进程存活(强制退出会丢未保存内容),把静默失败变可见。客户端 `runHostCommand`
   对未知 command 安全忽略,改动是纯增量。

2. **突发批量变更下的累积退化(已修):** `queuedRoamSyncChangedFiles` 原为数组 +
   每次 `Array.includes` 去重,大批量外部变更(如 `git checkout` 数百篇)push 是 O(n²)。
   改为 `Set` 去重(O(1)),同步时 `[...set]` + `clear()`。语义不变。

3. **其余累积量已受控:** `dirtyNoteFiles` 每次 scan 排空、受 vault 规模上界;
   `recentSelfWrites` 已 cap 256;路径/代码缓存均有字节或条数上限。无需改。

## 笔记系统:md 作为构建逻辑

md 作 source-of-truth、preview 作视图、补全后端实时查询 —— 设计恰当且可长期演进。
工作树里 `init-md-roam.el` 新增的 `:ddl` 逐行正则提取属行级受限,无性能问题,保留。

**仅记录、不动(尊重"不改 UX"):** Emacs 侧
`my/aaronnote-roam--scan-file-todos` / `--extract-links-from-buffer` / `--heading-items`
都 `widen` 后同步全缓冲扫描。不在打字路径上(编辑在 web app),但若用户**在 Emacs 里
直接打开 5MB md** 再触发 todos/links 命令会短暂卡 UI。低频路径;未来可选:改 idle 分片。

## 今日新功能可靠性审计(s-jump 及其余)

按用户要求,对今天提交/改动的功能做了代码质量与资源生命周期审计(计时器/监听器/
观察器是否清理、teardown、异步竞态、错误吞没)。初审发现 s-jump 候选截断；随后的
真实手感回归又暴露了 Vim inclusive selection / insert→Esc / 文档行移动，以及不完整
TeX delimiter 被 Escape preview 隐藏的问题，现均已补回归测试修复。

**s-jump(`vim-jump.ts` + `vim-lite.ts`)—— 初审缺陷,已修:**
`candidatePositions` 在可见区从上往下凑满标签预算就 `return`(截断发生在 `orderedPositions`
按方向排序**之前**)。后果:光标在屏幕下方、按 `s` 向前跳一个常见字符时,标签名额被
光标上方的匹配占满 → 前向候选可能为空或漏掉最近目标。这正是「按 s 跳得莫名其妙」的根因。
- 体验对齐 Emacs `avy-goto-char-timer`:`s` 向后/下、`S` 向前/上;可连续输入小写字符,
  timeout 后出小写标签;正文匹配大小写不敏感,搜索输入和标签键只接受小写。
- 修复:`candidatePositions` 收集全部可见匹配(安全上限 4096),排序后生成 prefix-free
  多级标签；近处尽量保持单键，超过单键字母数的候选使用两键/多键，不再截掉可视区目标。
  `to` 使用 `needle.length`。抽出纯函数 `selectJumpCandidates` / `buildVimJumpLabels`
  便于测试，并由 `tests/cm6/vim-jump.test.ts` 守护。
- 次要(均 fail-safe,未改):`applyVimJump` 重复 `clearVimJump`(无害);按 `s` 后无
  「等待字符」提示;两键间被 SSE `reloadNotes→setMarkdown` 改写时标签先消失但 fail-safe 清理。

**Vim / 输入桥后续审计——已修:** 普通与 Visual 的 `j/k` 过去用 UTF-16 文档列手算，
既不认识 CM6 折行，也会拆开 emoji/组合字符；Visual 的 CM6 half-open selection 与 Vim
inclusive head 混用，导致当前字符、反向扩选、鼠标/Shift-click 互转不稳定。现在字符边界
集中到 `text-boundaries.ts`，Vim 内部保存 inclusive anchor/head，垂直移动委托 CM6 的
`moveVertically`。`i/a/I/A/o/O` 的 Escape 落点分开处理，`I` 回到首个非空白字符；
Cmd+方向键不再被桥接为 windmove。

**公式反斜杠视觉消失——已修:** `\]` 在剪切/粘贴或后接文本的瞬间不再满足独占行的
块公式规则，Lezer 会把它临时识别为 Markdown `Escape`；preview 隐藏 escape slash，造成
“源码被吃掉”的错觉。source 实际未丢。live-preview 现在永不折叠 Noema 的
`\[`/`\]`/`\(`/`\)` delimiter，普通 `\*` 等 Markdown escape 行为不变。

**其余今日功能 —— 质量良好,无需改:**
- **floating-toc 标题搜索**(`floating-toc.ts`):`searchInput` 只创建一次;每次渲染
  `replaceChildren` 让旧按钮连同监听器一起 GC,无监听器泄漏。小注:同名同级标题的
  fold-key 可能碰撞(点击解析到首个);大文档每次 update 的 O(headings) 签名串拼接。非可靠性问题。
- **图片布局工具栏**(`widgets/image.ts`):悬浮工具栏每次 `toDOM` 重建,监听器随 DOM
  GC;`img.load`/`iframe.load` 回调前都查 `wrap.isConnected` 再 `requestMeasure`;装饰构建
  viewport 受限,选区 key ≤50 行短路。无泄漏。
- **@@todo 内联数学**(`widgets/inline-commands.ts`):`TodoWidget` 用与表格单元同一个
  共享渲染器 `renderMarkdownHTML`(本地笔记内容,已消毒)填 `innerHTML`;widget 有 `eq()`
  防重建;viewport 受限。无监听器。
- **getMarkdown 缓存**(`editor-cm6.ts:532`):按不可变 `Text` 身份 memoize,只钉住当前
  文档的一份字符串(换文档即替换,GC),非泄漏。
- **移除 React app-chrome / vim cursor overlay**:grep 全仓**无任何遗留引用**,清理彻底。

> 共性观察(非 bug):live-preview / image / inline-commands 等多个 ViewPlugin 每次
> docChanged 各自跑一遍 viewport `syntaxTree.iterate`。均 viewport 受限,叠加但可接受。
