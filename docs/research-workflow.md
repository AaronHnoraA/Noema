# Guided research workflow

Noema now has two starting templates: `empirical` (literature → experimental design → reproduction → evidence → paper) and `theoretical` (literature → proof plan → derivation/review → evidence → paper). Both are ordinary `.noema` WorkDocuments, not Jupyter notebooks. Their graph has stable WorkNode identities and lineage edges. The template is materialized in one validated file write only after the user accepts the preview; agent-generated structural changes still require the existing `graph.declare` Proposal and revision-fenced review path.

Open `M-x noema-project-overview` and select **New workflow**, or run `M-x noema-research-workflow-preview`. Choose the type, target file and title. Inspect the nine stages, then press `C-c C-c` to create or `q` to cancel. An existing target is never overwritten.

In the document, `C-c j N` visits the first unfinished stage. Run a work block with the normal `C-c C-c`; the template's `@@skill(...)` selects the relevant reusable research Skill and Noema resolves its dependencies before preparing the Run. Mark finished work `done` with the existing `C-c C-t` state action. At a review checkpoint, a person verifies the source material, then presses `C-c j A` and confirms. The approval marker is written into the checkpoint's source as an undoable document edit. A later template-stage Agent Run is refused until preceding work is done and checkpoints have been reviewed. This is a guided, local workflow gate; it does not pretend to authorize scientific claims or replace the existing Proposal/permission review paths.

Evidence is not inferred from prose. Save literature notes and raw experiment or proof artifacts, use `evidence-synthesis` to propose Findings backed by content-addressed evidence spans, and accept Findings through Attention. `M-x noema-findings` lets you inspect accepted claims, verification levels and exact artifact byte ranges. The final checkpoint asks a human to check claim–evidence alignment, figure/table provenance, citations, reproducibility and venue requirements before submission. `M-x noema-sessions` reuses named agent conversations; `M-x noema-capability-manager` controls global and project Skills/MCPs. `M-x noema-history-search` searches the project-scoped FTS5 index of native agent transcripts without changing those originals.

The template does not automatically dispatch every Run or submit a paper. Agent execution, data access, citations, and final publication remain explicit user actions. Existing non-template `.noema` documents keep their prior behavior.

## Reviewed memory in agent Runs

After a work block has a persisted Run output, `C-c j i` opens its Inspector. The **Run context** section reads the immutable RunSpec for that output's Run, showing the selected references, byte sizes, Finding versions, truncation and omission reasons, and the RunSpec digest. It remains attached to that Run even when the source document or Findings change later. A `preparing` Run has frozen inputs but has not dispatched them. The receipt describes what Noema selected for dispatch; an ACP agent may add its own context, which Noema cannot inspect.

The Inspector also shows **Upstream now**, a read-only comparison with the current saved `.noema` document. For each `result:` reference actually selected for the Run, it reports an unchanged output, a changed output from the same Run, a different Run output, a missing output, or an output that cannot be verified. A truncated output now freezes the digest of its complete source as well as the delivered excerpt; older truncated RunSpecs without that digest remain unverifiable when the Run id has not changed. If the saved document cannot be read, the comparison says so and the frozen receipt remains available. This comparison never changes a WorkNode state or the old RunSpec; unsaved editor edits are outside its view.

When an ACP adapter reports usage at the Run's terminal event, the receipt also shows that timestamped **cumulative Session** snapshot. It is not a per-Run token charge. Older Runs and adapters without usage report "unavailable"; the Inspector does not substitute the Session's current usage, since a later Run could have changed it.

agent-shell's initial zero counters are not a usage report. Noema records a Run's usage only when that ACP buffer reports token counts or a context window after the Run starts. If a Run ends without a fresh report, its receipt has no usage snapshot and Noema clears the Session's previous context reading. The next preview then shows usage as unavailable instead of deciding rollover from a stale measurement; earlier Run receipts keep their frozen snapshots.

Before dispatch, `C-c j p` shows the selected Session's latest reported ACP context use, window size, report time and effective rollover threshold. The default threshold is 85% and can be set through `noema-agent-worker-context-rollover-ratio` from 50% to 99%; out-of-range values use 85%. A missing window is shown as unavailable, without inventing a 0% reading or requesting automatic rollover. An already pending rollover is shown separately and still reconstructs the next Run from its latest durable Handoff. The preview only observes this decision; it does not request compaction.

Agents can inspect the same bounded receipt through `research_run {action: "context", id: RUN_ID}`. For DAG planning, `research_cell {action: "outline"}` returns direct lineage and dependency neighbours with state, latest Run id, content sizes and digests, without copying their source or outputs into the agent's tool result. `read` and `neighbors` remain available when full content is needed. Outline and full-neighbour responses omit `local_only` neighbours; reading a `local_only` cell is refused.

Run preparation now selects up to three relevant Findings from the same workstream. Only project-disclosed Findings with `supported` or `accepted` status, evidence spans, and `reproduced`, `human_reviewed`, or `formally_verified` verification qualify. Weak lexical matches produce no memory context. Chinese Han bigrams and Latin identifiers are both searched. Each selected item freezes the Finding id, version, statement, verification level and evidence artifact spans into the RunSpec. The context preview lists these as automatic `finding:<id>` references. Declared context and lineage take priority under the existing 64 KiB limit; `@@ctx(none)` disables this recall. A memory lookup failure does not stop a Run.

The recall query uses at most 32 distinct terms in source order. For a longer work prompt it keeps 16 terms from the beginning and 16 from the end, so a long reference list cannot hide the final task. Selected Finding snippets share a 3,600-byte UTF-8 budget before the Run's overall context budget is applied; this counts Chinese and Latin content in the same units as the 64 KiB limit.

At a DAG merge, Noema attaches the latest output of each direct lineage parent before older source cells and recalled Findings. Explicit `@@ctx(...)`, the project header and selected capabilities consume the 64 KiB Run context budget first. Automatic items that fit are kept whole; when multiple parent outputs compete for the remainder, Noema reserves up to 1 KiB per parent (or the full output if smaller), then shares the remaining space across the parents awaiting excerpts. If these minimum excerpts do not fit, the RunSpec records which parent outputs and lower-priority items were omitted and why. Truncation and omission are visible in the context preview and the Inspector receipt. A new `@@session(fresh)` conversation also receives its DAG lineage; `@@ctx(none)` remains the explicit opt-out.

When the remaining budget cannot cover every parent, the merge fits as many parents' minimum excerpts as possible. Complete short outputs cost their actual byte size; ties follow the document's parent order. The context preview shows each truncated excerpt's original size and each omission reason, so the allocation can be checked before dispatch.

Truncated parent outputs and Handoffs retain both their beginning and end, with a marker where the middle was removed. This keeps the final outcome visible under a tight budget. Other automatic references retain a leading excerpt.

`depends` edges express ordering, so their outputs are attached only when the block declares `@@ctx(depends)` (or names a `result:<work-node-id>` explicitly). This keeps a readiness dependency from silently becoming prompt content.

When a fork must be reconstructed from a parent Session, its parent output and Handoff follow the same automatic-context budget as DAG lineage. A large Handoff is truncated or omitted with a recorded reason after declared references take their space. `@@ctx(none)` suppresses both reconstructed sources, including after a Session rollover.

To turn an exact excerpt from a completed Run's Handoff into a reusable decision or lesson, run `M-x noema-research-propose-memory-from-run`. Enter the Run id, kind, excerpt and disclosure. The command records a pending `finding.create` Proposal with the exact Handoff byte range as evidence. Open Attention, read its **Handoff evidence** button, and accept only after checking the statement. Acceptance records `supported` and `human_reviewed`, including when it confirms a prior provisional Finding with the same statement. A rejected or `local_only` proposal never enters automatic recall. The command requires an existing Handoff artifact and does not synthesize a statement from the Run transcript.
